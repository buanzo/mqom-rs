# Hardening record

This record describes engineering checks performed for the frozen
`MQOM2-L1-gf16-short-r5` profile. It is not an independent cryptographic audit
and does not change the project's experimental, non-production status.

## Interoperability and negative tests

- Native key generation and signing reproduce all 100 official MQOM v2.1.1
  KAT keypairs and signatures byte-for-byte.
- The upstream `kat_check` executable accepts the response generated by Rust.
- The oracle harness rejects targeted changes in the salt, commitments,
  response, opening, nonce, message, and public key.
- Default Rust tests exercise the same signature regions, invalid encoded
  lengths, inconsistent imported signing keys, and failing randomness sources.

Generated KAT material and the C oracle remain under ignored `target/` storage;
neither is part of the repository or crate package.

## Fuzzing surfaces

The separate, package-excluded `fuzz/` project contains two `cargo-fuzz`
targets:

- `public_api` exercises all public parsers and signing-key consistency checks.
- `verify` fixes the public-key and signature boundaries, then passes the
  remaining bytes as the message to the complete verifier.

Build or run them with a current nightly toolchain:

```console
cargo +nightly fuzz build
cargo +nightly fuzz run public_api
cargo +nightly fuzz run verify
```

CI compiles both targets and audits their separate lockfile. A compiled target
and a short local smoke campaign are regression evidence, not a substitute for
a sustained, independently reviewed fuzzing campaign.

## Secret-state and timing review

- The crate forbids unsafe Rust and has no FFI or C-backed runtime.
- Secret key encodings redact `Debug` output and clear their owned storage on
  drop.
- Key-generation seeds, signing randomness, packed secret vectors, GGM tree
  nodes, leaf expansions, polynomial masks, and intermediate alpha values use
  explicit zeroization wrappers or drop implementations.
- GF(16), GF(256), and GF(256^2) arithmetic uses fixed-iteration operations;
  equality checks for commitments use `subtle` constant-time comparisons.
- Public parsing and verification may reject early. Signing's grinding loop is
  variable-time over a nonce that is included in the public signature, matching
  the protocol's rejection-sampling boundary.
- AES and SHAKE behavior ultimately depends on the selected RustCrypto backend,
  compiler, and target CPU. No formal constant-time proof, leakage measurement,
  locked-memory guarantee, or claim about eliminated compiler copies is made.

The signing path expands one GGM tree at a time and clears it before processing
the next execution. This bounds live tree storage instead of retaining all
twelve trees simultaneously.

## Portability, dependencies, and packaging

- CI tests Linux, macOS, and Windows and checks Rust 1.85 as the MSRV.
- The library is checked as `no_std + alloc` for `wasm32-unknown-unknown` and
  `thumbv7em-none-eabihf`.
- `cargo deny` and `cargo audit` cover both the main and fuzz lockfiles.
- Repository policy rejects files over 5 MiB, vendored C/header files, and KAT
  request/response files; package contents are checked independently.
- A Criterion-free performance harness, using the operating system RNG through
  `getrandom`, is available through `cargo bench --bench profile`. It is for
  regression measurement, not side-channel analysis.

## Release gates still open

The crate remains version `0.0.0` with `publish = false`. A `0.1.0` release
still requires all of the following:

- independent cryptographic and side-channel review;
- professional review of licensing and contribution governance;
- revalidation of the intended crates.io name and release artifacts; and
- explicit release approval from Arturo Busleiman aka Buanzo.
